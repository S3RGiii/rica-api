# L8 — CQRS: `consultas-service`

**Rama:** `taller-l8-cqrs` (base `taller-microservicios-lineal`)
**Objetivo:** separar el lado de lectura del lado de escritura sin compartir base de datos ni llamadas síncronas.

## Componentes

| Servicio | Lado | Qué hace en L8 |
|---|---|---|
| `investigadores-service` | Escritura | Publica `investigadores.registrados`, `investigadores.en-eliminacion` y `investigadores.eliminados` |
| `publicaciones-service` | Escritura | Publica `publicaciones.registradas` después de guardar |
| `consultas-service` | Lectura | Consume los cuatro eventos y mantiene una ficha por investigador en `rica_consultas` |
| `gateway` | Entrada | Ruta `lb://consultas-service` para `/api/consultas/**` |

## Modelo de lectura

`FichaInvestigador` es un documento de MongoDB (`fichas_investigador`) con:

- `correo` como `_id`.
- `nombreCompleto` (puede ser `null` si el evento de publicación llega antes que el de registro).
- `estado`: `ACTIVO` o `EN_ELIMINACION`.
- `publicaciones`: lista desnormalizada de `ResumenPublicacion`.
- `totalPublicaciones`: guardado para poder ordenar el ranking en MongoDB.

No es la fuente de verdad: se puede borrar y reconstruir reproduciendo los eventos.

## Proyector y garantías

`ProyectorFichas` traduce cada mensaje JSON a un cambio sobre la ficha:

- **Idempotente:** `agregarPublicacion` ignora una publicación cuyo `id` ya está en la ficha.
- **Tolerante al desorden:** una publicación que llega antes del registro crea la ficha vacía; el nombre se completa cuando llega `investigadores.registrados`.
- **Sincronizado:** los métodos son `synchronized` porque cada tópico tiene su propio hilo consumidor y dos eventos del mismo investigador podrían pisarse al leer-modificar-guardar. Con varias instancias haría falta bloqueo optimista (`@Version`).
- **Eliminación:** `investigadores.en-eliminacion` marca `EN_ELIMINACION`; `investigadores.eliminados` borra la ficha.

## Endpoints

```http
GET /api/consultas/investigadores
GET /api/consultas/investigadores?estado=EN_ELIMINACION
GET /api/consultas/investigadores/{correo}
GET /api/consultas/ranking?top=3
GET /api/status
```

No hay operaciones de escritura en este servicio. Un correo sin ficha responde **404** mediante `GlobalExceptionHandler`.

## Reconstrucción

1. Detener `consultas-service`.
2. Borrar la colección:
   ```powershell
   docker exec -it publicaciones-mongo mongosh rica_consultas --eval "db.fichas_investigador.drop()"
   ```
3. Cambiar `spring.kafka.consumer.group-id` a un grupo nuevo (por ejemplo, `consultas-service-v3`).
4. Arrancar de nuevo. Con `auto-offset-reset: earliest`, el grupo nuevo reproduce los eventos desde el principio.

Las publicaciones anteriores a L8 no se pueden reconstruir porque `publicaciones-service` no publicaba `publicaciones.registradas` antes de este cambio.

## Configuración

- Puerto: `8083`.
- MongoDB: `mongodb://localhost:27017/rica_consultas` con `spring.mongodb.uri` (Spring Boot 4).
- Kafka: `localhost:9092`, `group-id: consultas-service-v2`, `auto-offset-reset: earliest`.
- Eureka: `http://localhost:8761/eureka`.

## Pruebas

```powershell
cd consultas-service
.\mvnw.cmd test
```

**Resultado verificado:** 7 tests verdes (3 de `FichaInvestigadorTest` + 4 de `ProyectorFichasTest`).

Los tests son unitarios: no levantan Spring, Kafka ni MongoDB. La prueba end-to-end del taller (ficha con publicaciones, ranking, caída del lector, Saga y reconstrucción) se ejecuta manualmente con la infraestructura arriba y **no se reporta como ejecutada** en este documento.
