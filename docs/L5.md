# Paso L5 — separación en dos servicios

Este documento deja explícito el paso intermedio entre el monolito hexagonal (L4) y el taller de gRPC (L6). El código L5 se trabajó localmente en `Talleres/Leccion-05-Microservicios/rica-microservicios`; esa copia no era un repositorio git, así que no tiene un commit propio. Su estado quedó reflejado en los módulos de esta rama.

**Fecha del trabajo local:** previa al commit L6 `3f69c37` (2026-10-20).
**Evidencia de pruebas:** 9 tests verdes (7 de investigadores + 2 de publicaciones) y 7 requests Bruno.

---

## 1. Dos servicios, dos bases

| Servicio | Puerto | Base | Responsabilidad |
|---|---:|---|---|
| `investigadores-service` | 8080 | PostgreSQL `rica` | Registro, consulta y límite de publicaciones por investigador |
| `publicaciones-service` | 8081 | MongoDB `rica` | Registro y consulta de publicaciones |

Cada servicio tiene su propio `pom.xml`, su `application.yml` y su `docker-compose.yml`. No comparten proceso ni base.

---

## 2. El puerto que rompe el acoplamiento

En L4, `PublicacionService` dependía directamente del repositorio de investigadores:

```java
private final InvestigadorRepository investigadorRepository;

if (!investigadorRepository.existsByCorreoInstitucionalValor(
        publicacion.getInvestigadorCorreo())) {
    throw new RecursoNoEncontradoException(
        "No existe un investigador con correo " + publicacion.getInvestigadorCorreo());
}
```

En L5 se declara un puerto local:

```java
package com.rica.publicacionesservice.publicaciones;

public interface VerificadorInvestigador {
    boolean existe(String correoInstitucional);
}
```

Y `PublicacionService` pasa a depender del puerto:

```java
private final VerificadorInvestigador verificadorInvestigador;

if (!verificadorInvestigador.existe(publicacion.getInvestigadorCorreo())) {
    throw new RecursoNoEncontradoException(
        "No existe un investigador con correo " + publicacion.getInvestigadorCorreo());
}
```

El núcleo de publicaciones ya no importa `rica_api.investigadores` ni JPA. Solo conoce el contrato.

---

## 3. El adaptador pendiente

Mientras el contrato de red no existe, se usa un adaptador deliberadamente incompleto:

```java
@Component
public class VerificadorInvestigadorPendiente implements VerificadorInvestigador {

    @Override
    public boolean existe(String correoInstitucional) {
        return true; // TODO L6: reemplazar por un adaptador gRPC real
    }
}
```

**Por qué devuelve `true`:** permite que `publicaciones-service` arranque y que los tests del resto del flujo no dependan de un servicio que aún no existe. No es una solución: es un marcador visible. En L6 se reemplaza por `VerificadorInvestigadorGrpc`.

---

## 4. Qué se prueba en L5

- `InvestigadorFactoryTest` — 3 tests de creación del agregado.
- `InvestigadorServiceTest` — 4 tests del caso de uso.
- `LimitePublicacionesAnualesServiceTest` — 2 tests del límite anual.

Total: **9 tests verdes**. El adaptador pendiente no se prueba contra un servidor real; esa es la deuda que paga L6.

**Bruno:** 7 requests (listar/crear/status de investigadores; crear con correo real, crear con correo inventado, listar y status de publicaciones). El caso “correo inventado” solo devuelve 404 cuando el adaptador real existe; con el pendiente, el flujo llega hasta el límite anual.

---

## 5. Transición a L6

| L5 | L6 |
|---|---|
| `VerificadorInvestigadorPendiente` | `VerificadorInvestigadorGrpc` |
| Puerto local | `InvestigadorGrpcBlockingStub` + `investigador.proto` |
| Sin red | gRPC en `localhost:9090` |
| Sin deadline | `withDeadlineAfter(5, TimeUnit.SECONDS)` |
| Sin breaker | Resilience4j Circuit Breaker |
| 9 tests de dominio/aplicación | Mismos 9 tests + verificación manual con `grpcurl`/Bruno |

`PublicacionService` no cambia entre L5 y L6. Ese es el punto: el puerto aísla al núcleo de la tecnología.
